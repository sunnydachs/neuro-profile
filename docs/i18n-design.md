# i18n（英語対応）設計ドキュメント

> 状態: **設計案（未実装）** / 2026-09-05
> 目的: 日本語オンリーの現状から、海外アクセスに備えて英語版を追加する。

---

## 1. 目的と結論

- 日本語版をデフォルトのまま維持しつつ、英語版を追加したい。
- 端末（ブラウザ）設定からの**自動切替**と、**下部の言語セレクタ（手動切替）**の両方が欲しい。
- どちらも標準的な i18n 手法で**十分実現可能**。むしろ本サイトは静的クライアントアプリなので、
  サーバーサイド i18n フレームワーク不要で、比較的シンプルに実装できる。

---

## 2. ベストプラクティス（調査結果）

言語を「どれを表示するか」決める順序は以下が確立された定説
（W3C / Smashing Magazine / i18next すべて一致）。優先度の高い順:

```
1. URL（例: /en/、/ja/）              ← 共有・検索・ブックマークが壊れない
2. ユーザーの明示的な選択（セレクタ or localStorage）
3. ブラウザ設定（Accept-Language／navigator.languages）
4. フォールバック（デフォルト = ja）
```

- **自動検出（ブラウザ設定）は「初期値の決定」だけに使う**。強制や恒久判定にしない。
- **言語セレクタ（手動切替）は i18n の鉄則**。ユーザーに逃げ道を常に提供する。
- OGP / meta / title も言語に合わせて切り替える（SNS シェアの崩れを防ぐ）。
- `hreflang` で言語版同士を相互参照し SEO を通す。
- 英語は LTR なので `dir` の変更は不要（RTL 言語対応は対象外）。

---

## 3. 最重要の前提: データの二重管理を解消する

現在、プロフィール等の文章が **2 箇所に存在**している:

| 場所 | 内容 | 使うファイル |
|---|---|---|
| `data/*.json` | 質問・軸メタ・16 タイプ全文 | `type.js` / `types.js` が fetch |
| `app.js` 冒頭のインライン定数 | `QUESTIONS` / `AXIS_META` / `PROFILES` | `app.js`（file:// 互換のため） |

英語化を始める前に、**どちらを source of truth に統一するか**を決める必要がある。
翻訳を二重管理すると不整合が必ず起きる。

### 推奨: `data/*.json` を唯一の正にする

- `app.js` のインライン埋め込み（`QUESTIONS` / `AXIS_META` / `PROFILES`）を廃止し、
  `type.js` / `types.js` と同様に `data/*.json` を `fetch` して使うよう統一する。
- 注意点: 現状 `app.js` は `file://` 直開きでも動くよう「インライン埋め込み」を選んでいる。
  JSON fetch に切り替えると `file://` では CORS で動かなくなるため、
  「ローカル静的サーバ必須」という制約が付く（README 更新が必要）。
  → オンライン配信 (Cloudflare Pages) が本番なので、このトレードオフは許容。

## 4. 翻訳データの持ち方

### 案 C（推奨）: 構造と文言を分離

- `id`・`axis`・`polarity`・`reversed`・`kind` などの**構造（ロジックに使う値）は共通 1 箇所**。
- **文章・表示文言だけ**を `ja` / `en` で持つ。

```jsonc
// questions.json（案 C の形）
{
  "structure": [
    { "id": 1, "axis": 1, "polarity": "E", "reversed": false, "kind": "regular" },
    ...
  ],
  "text": {
    "ja": { "1": "新しい場所や未知の状況にワクワクする", ... },
    "en": { "1": "I feel excited about new places and unfamiliar situations.", ... }
  },
  "scale": {
    "ja": { "5": "非常に当てはまる", ... },
    "en": { "5": "Strongly agree", ... }
  }
}
```

- 理由: スコアリングは言語に無関係なので、構造を共通化すれば
  「英語版だけ逆転項目の扱いがズレる」等のバグを構造的に排除できる。

### 案 B（代替）: 言語キーで丸ごと同居

```jsonc
{ "ja": { "questions": [...], ... }, "en": { "questions": [...], ... } }
```

- 差分は見やすいが、`id`/`reversed` 等のロジック値まで言語ごとに複製されるため、
  構造と文言の乖離リスクがある。→ 推奨は案 C。

### 案 A（非推奨）: 言語別ファイル分離（`data/ja/...`, `data/en/...`）

- 二重管理そのものを助長する。採用しない。

## 5. URL 構造

### 推奨: サブディレクトリ方式

```
/        … 日本語版（現状のまま）
/en/     … 英語版
```

- 既存の公開済み URL（`index.html` / `types.html` / `type.html` / `og/type-XXXX`）は
  すべて日本語版として**維持**する（既存シェアリンク・OGP を壊さない）。
- `/en/` 配下に英語版の各ページを置く。
- Cloudflare Pages の「クリーン URL（.html を 308 する）」挙動を考慮し、
  リンク・og:url は拡張子なしか、`/en/` 配下パスを明示する。

### 検討事項

- 言語セレクタで `/en/` へ切り替える際、現在ページの対応ページへ飛ばす
  （例: `types.html` → `/en/types.html`、`og/type-EAND` → `/en/og/type-EAND`）。

## 6. 実装方針（段階）

1. **source of truth 統一**: `app.js` のインライン定数を `data/*.json` fetch へ置換。
2. **i18n レイヤー追加**:
   - 新規 `app/i18n.js`（言語決定・切替・localStorage キャッシュ）。
   - `navigator.languages` で初期言語を決定（明示選択があれば優先）。
3. **言語セレクタ実装**: `app-nav.js` に「日本語 / English」スイッチャー追加
   （ヘッダー下部もしくは右下固定）。
4. **`<html lang>` / title / meta og:locale の動的切替**。
5. **hreflang 相互参照**（`ja` ↔ `en`）。
6. **英語翻訳の投入**（質問 50 問・軸メタ・16 タイプ全文・UI 文言・共有テキスト）。
7. **OGP ページ & 生成スクリプトの英語対応**（`scripts/gen-type-pages.js` で /en/ 版も生成）。
8. **テスト**: 言語切替・`hreflang`・スコアリング非依存性の確認。README 更新。
